3. Context and Scope

Content: System scope and context delimits your system (its scope) from all its communication partners (neighbouring systems and users, its context), and specifies the external interfaces. If useful, separate the business context (domain inputs and outputs) from the technical context (channels, protocols, hardware).

Motivation: The domain and technical interfaces to communication partners are among a system's most critical aspects. Make sure you completely understand them.

Form: Various context diagrams; lists of communication partners and their interfaces.

3.1 Business context

Content: Specify all communication partners (users, IT systems) with domain-specific inputs and outputs. Optionally add domain formats or protocols.

Motivation: All stakeholders should understand which data are exchanged with the system's environment.

Form: Diagrams showing the system as a black box with domain interfaces to partners, or a table (system name as title; columns: partner, input, output).

Example: HTML Sanity Checker

A simple business context, drawn as a black box with its neighbours.

Communication partners and what they exchange with the checker.
NeighbourDescription
UserDocuments software with a toolchain that generates HTML; wants valid links.
Build systemUsually Gradle; runs the checker as part of the build.
Local HTML filesThe checker reads and parses local HTML and runs sanity checks.
Local image filesThe checker verifies that linked images exist as local files.
External web resourcesOptionally checks that external links resolve (slower, network-dependent).

3.2 Technical context

Content: Technical interfaces (channels and transmission media) linking the system to its environment, plus a mapping of domain I/O onto those channels.

Motivation: Many stakeholders decide architecture from technical interfaces, especially infrastructure and hardware designers.

Form: For example a UML deployment diagram of channels to neighbours, with a mapping table from channels to input/output.
