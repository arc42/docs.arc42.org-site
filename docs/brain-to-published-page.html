Brain to Published Page

How a page in our second brain becomes a page on the website — and why changing one, afterwards, is deliberately not easy.

The second brain does not build the website. It writes the website's source files — and then the website gets built exactly the way it always was.

That one sentence is the whole arrangement. Jekyll, the program that turns our Markdown into the HTML a reader sees, never looks inside the brain. It only ever sees the ordinary content files in _pages/, _posts/ and _examples/, just as it did before the brain existed. What changed is who writes those files: for the sections we have handed over, a generator writes them from the brain. For the rest, they are still the files we wrote by hand years ago.

We edit docs-arc42-brain/wiki/ 294 pages, in Obsidian
→ make generate
Jekyll's input _pages/ _posts/ _examples/ 74 files + 28 images
→ make dev
Readers see _site/ 199 pages of HTML

So "creating the site from the brain" is two commands, and the first one is the only one that is new:

$ make generate # brain → the website's source files $ make dev # source files → the site, at http://localhost:4210
Worth knowing

make generate is safe to run at any time. It writes only what actually changed, and if nothing in the brain changed it says so. Run just now, it reported 0 written, 0 deleted, 102 unchanged — the 74 content files plus 28 images it is responsible for.

01Two worlds, one repository

Everything lives in the same repository, in two neighbouring folders. The brain holds one page per thing, richly cross-linked; the site holds one file per URL. They are not the same list, and that difference is deliberate.

In the brainPagesWhat becomes of it on the site
wiki/sections/12_pages/section-N.md — one per arc42 section
wiki/tips/144_posts/06-runtime/… — one per tip
wiki/examples/35_examples/… — one per example
wiki/terms/43No page. A term lends its name to the tags on tips
wiki/keywords/12No page. Same — and the /keywords/ index builds itself from them
wiki/systems/4No page. The example systems, as a shared reference
wiki/issues/44No page. Our own list of open questions and known defects

That is why the brain has 294 pages but writes only 74 files: more than half of the brain is vocabulary, worklist and provenance — the scaffolding that keeps the published half consistent. It is for us, not for the reader.

What the generator did, in plain terms

  • Vocabulary became tags. One keyword, [[thorough]], and two terms, [[runtime-view]] and [[runtime-scenario]], collapsed into the single line tags: thorough runtime-view runtime-scenario. The name of the vocabulary page is the tag — which is how we stopped having both runtime and runtime-view mean the same thing.
  • Links became a "see also" block, spelled out. In the brain we write [[tip-6-3]] and nothing else. The generator knows that page's real title and its real URL, so it writes both into the published file. If we rename a tip, every "see also" that points at it is corrected everywhere, by regenerating.
  • The section link became the first see-also entry. A tip always points back to its section; we never type that link twice.
  • A warning line was added. The last line of the header says where this file came from and not to edit it.
Why the warning line sits in the header

It has to live inside the front matter, not in the text. As a line of body text it would be picked up as the page's excerpt — and would wipe out the description search engines show.

03What else gets translated

Section pages need more work than tips, because the published section pages contain a handful of instructions for Jekyll — written in curly braces, a little language called Liquid. The brain contains none of it, by rule, so that a brain page stays plain, readable Markdown that renders correctly in Obsidian. The generator puts the machinery back.

04A page only reaches the site when we say so

Every brain page carries a status, and it climbs one ladder:

draft → review → published → retired └── only this one reaches the website

This is the switch that makes the whole transition gradual and safe. A section can be fully written up in the brain — every tip, every example, every term, all cross-linked and checked — and still be completely invisible to readers. Nothing happens until we flip it to published and regenerate.

A small surprise

Terms and keywords keep their own status forever and it does not matter. thorough is still a draft page in the brain, yet the published tip 6-4 carries thorough as a tag — because vocabulary pages never become pages on the site. Only sections, tips and examples have a status that readers can feel.

05Four rails that keep it honest

A generator that overwrites a live, widely-cited website is only as good as what stops it. There are four independent checks, and each exists because of a specific way this could go wrong.

It must reproduce today's page first

Before a section is handed over, the generator writes it into a scratch folder and compares it, line by line, with what is on the site right now. Differences in the text are never accepted — they are a bug in the brain page or the generator. Only tag changes are allowed through, and they get written into the pull request.

make generate-check SECTION=6

Nobody can edit the output

The warning line in each generated file is also a lock. The generator refuses to overwrite a file that does not carry it — so a hand-written original can never be clobbered by accident — and a separate check fails the build if a generated file was edited directly, instead of its brain page.

make brain-check-generated

Published URLs can never vanish

Every URL the generator has ever published is recorded — 74 so far, and the list only ever grows. If a change would stop one of them being served, the generator stops. The site has no forwarding mechanism, so a dropped URL is a dead link for everyone who ever cited it. Retiring one on purpose means writing down the reason. So far: none.

_system/published-permalinks.txt

Changing published text needs a yes

An immutable copy of every page as it was before hand-over is kept. Any later change to published text is compared against it — so a deliberate correction looks exactly like a generator malfunction. The fix is to show the change as a before/after and approve that one change explicitly.

make brain-approve-edit

06Hand-over: the one-time ceremony per section

Generating is routine and happens constantly. Hand-over happens once per section, as its own pull request, and it is the moment responsibility for that section's text moves from the old files to the brain. In order:

  1. Prove it reproduces the page.

    The comparison must pass with no differences in the text. Every note it prints gets read: tag changes go into the pull request description, anything else is a defect to fix first.

  2. Flip the statuses to published.

    The section page, each of its tips, each of its examples. Terms, keywords and systems are left alone — they are not pages on the site.

  3. Delete the hand-written originals.

    This feels alarming and is the crux of the whole design. It must come before the next step, precisely because the generator refuses to overwrite a file it does not own. Deleting them is how we consciously transfer ownership.

  4. Generate.

    The files reappear at the very same paths, now carrying the warning line and the "see also" block. Run it a second time: it must report nothing to do. The first run records the section's URLs in the permanent list.

  5. Run everything.

    The parity check, the unit tests, the site build and sanity checks, and the link checker. From here on, the regression net is the automatic comparison against the untouched copies taken at ingest.

  6. Write the log entry.

    One line in the brain's own log, so the history of what was handed over when is readable without digging through commits.

  7. One commit.

    Statuses, generated files, log. The diff should show header changes and nothing else — never a change to the text of a page. If it does, something is wrong.

07Afterwards: fixing a typo is a decision

Once a section is handed over, the brain owns its text — and correcting it is the entire point of having done this. But because an untouched copy of the original is kept as the regression net, a deliberate correction is indistinguishable from the generator quietly breaking. So a correction is shown and approved, one at a time:

$ make brain-approve-edit REL=_pages/section-9.md \ ISSUE=ISS-002 REASON="ADR table gains a Date row" … prints the before/after. Records nothing. $ # satisfied? the identical line again, with YES=1 $ make brain-approve-edit … YES=1

The approval is written down, with the issue that justified it:

Register_system/approved-body-edits.tsv
_pages/section-9.md   ISS-002   2026-09-23
  ADR table gains a Date row and an (optional) Criteria row,
  both marked as arc42 additions

Each approval covers exactly one version of one page — it is keyed to a fingerprint of the approved text, so the next change to the same page needs its own yes. That sounds heavy, and is meant to: this is a template thousands of teams copy, and its wording is the product.

The first real one

So far there is exactly one approved change: section 9's ADR table gained a Date row — when was this decision taken — and an (optional) Criteria row. Both are marked as arc42's own additions to Nygard's original structure.

08Making yourself a local copy to look at

Nothing of this has been published yet. To see the current state as a working website on your own machine:

$ make generate # only if you changed something in the brain $ make check # validate the brain, then build and sanity-check the site $ make dev # serve it, rebuilding as you edit

Then open http://localhost:4210 — written out in full, because Firefox refuses the 0.0.0.0 form the server prints. The curator dashboard runs separately on port 4211 and the two do not interfere.

The order matters for one reason only: make check validates the brain before building the site, so a broken brain page fails in seconds rather than after a full build. What you will be looking at is a deliberate mixture — five sections written by the brain, seven still the originals — and if the parity checks have done their job, you should not be able to tell which is which.

09Words that keep coming up

Jekyll
The program that turns our Markdown files into the HTML a browser shows. GitHub runs it for us on every push.
Front matter
The header block at the top of every content file, between two lines of ---. It is where title, URL, tags and layout live. Almost everything the generator does happens here.
Liquid
The small instruction language in curly braces that Jekyll understands — {% include … %}, {{ site.imageurl }}. The brain is kept completely free of it.
Permalink
The public URL of a page, e.g. /tips/6-4/. Treated as a permanent promise: these are cited from books, talks and other sites.
Slug
The short machine name of a brain page, taken from its filename — runtime-view. For terms and keywords, the slug is exactly the tag that appears on the site.
Wikilink
A link between brain pages, written [[runtime-view]]. Obsidian follows them; the generator turns them into real titles and URLs.
Parity check
Generating a section into a scratch folder and comparing it with the live site, without touching anything. Our proof that handing a section over changes nothing for readers.
